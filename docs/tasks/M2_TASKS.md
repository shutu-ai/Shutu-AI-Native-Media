## M2-T1 · 统一 Session/Track/Clock/Event/Policy 契约 v0.1 冻结

**1. Task ID 与目标**
把基线 §4 的逻辑契约落为 `contracts/media/v0.1` 并冻结：Session 状态机（§4.3）、Track 状态机、Graph 状态、AIJob 状态、MediaTimestamp/MediaFrameEnvelope 逻辑模型、Capability 结构、Policy 接口；配套可执行的契约测试（状态机转换合法性、时间戳语义、权限撤销语义）。

**2. 对应需求 FR / 架构 ADR**
- FR-004、FR-006；ADR-005（统一契约）、ADR-007（Provider 可替换的契约基础）；基线 §4.1~4.5、§9 M2-1。

**3. 前置依赖**
G1 = GO。

**4. 允许修改的模块与文件范围**
- 修改：`contracts/media/`（v0.1 定义 + 冻结记录）、`runtime/media-core/`（实现契约的类型与状态机）
- 新建：`tests/contract/`（媒体契约测试）

**5. 实施步骤**
1. 将 §4.2 逻辑结构转为 Rust 类型 + 序列化 schema（控制面允许富对象；热路径仍走 M1-T3 二进制布局，本契约不含热路径字符串字段）。
2. 实现四状态机并写转换表；非法转换显式拒绝。
3. 时间语义：会话运行时间轴 + 设备时钟域映射/漂移记录结构（§4.4）。
4. Policy 最小集：采集授权、AI 参与授权、旁路策略（§4.5 编排规则 1/5）。
5. 契约测试：状态机全转换覆盖、时间戳单调、撤销授权即时阻断语义。
6. 冻结记录：v0.1 tag + 兼容性承诺（变更需 ADR，§14.3）。

**6. 自动化测试要求**
- 状态机表驱动测试（每个合法/非法转换一个用例）；时间戳语义测试；契约测试纳入 CI。

**7. 真实环境验收要求**
- 契约测试为自动化（CI 级证据即可）；但「契约可用」的最终确认发生在 M2-T4 真机联合运行中。

**8. 完成标准（DoD）**
- v0.1 冻结入库；测试全绿；后续模块引用契约无 Windows 私有句柄暴露为公共 API（为 M6-T1 预留，§5.4）。

**9. 风险及失败处理**

**10. 应保留的测试证据**
`test-results.json`（契约测试）、`contracts/media/v0.1` 冻结记录、`build.log`。

## M2-T2 · 物理麦克风捕获、PCM 处理与同步测试源

**1. Task ID 与目标**
Runtime 增加音频路径：物理麦克风采集（48kHz/16-bit/mono 为 V1 参考格式，允许 OS 端协商）、PCM 最小处理链、同步测试源（测试卡 + 音频脉冲同时输出，为 NFR-04/05 同步测量提供标准素材）。

**2. 对应需求 FR / 架构 ADR**
- FR-005、FR-006；ADR-005；基线 §2.2（Track A 参考格式）、§9 M2-2、§7 NFR-02 测试条件（48kHz 单声道 10ms 音频块）。

**3. 前置依赖**
M2-T1。

**4. 允许修改的模块与文件范围**
- 修改：`runtime/gst-adapter/`（音频采集与处理链）、`runtime/media-core/`（音频 Track 接入）
- 新建：`tests/fixtures/`（同步测试素材生成器）、`tests/integration/`

**5. 实施步骤**
1. 物理麦克风采集：`wasapisrc`（共享模式）→ capsfilter（48kHz s16le mono）→ appsink；记录设备与采样率能力。
2. 采样率转换（audioconvert/audioresample）验证：非 48k 麦克风输入能重采样到参考格式。
3. 10ms 音频块（480 samples）边界测试：块大小、时间戳连续性。
4. 同步测试源：视频测试卡 + 音频脉冲在同一 Session 同时生成（脉冲时刻与画面标记帧对齐，供 NFR-05 测量）。
5. 音频指标：块计数、时间戳单调、断流计数暴露。

**6. 自动化测试要求**
- 集成测试：固定时长采集，块时间戳连续无跳变；SRC 精度（正弦输入频率保持）。

**7. 真实环境验收要求**
- **必须使用真实物理麦克风**；无物理麦克风时用带真实时钟的测试音源并显式记录差异（不得静默替代）。

**8. 完成标准（DoD）**
- 音频采集链稳定；SRC 与块边界行为有证据；同步测试源可复现生成。

**9. 风险及失败处理**
- 采集设备被独占（R-03 同型）→ 共享模式打开；失败显式报错。
- WASAPI 事件模式与时钟问题 → 记录实测行为与官方依据（[S17]），不猜测。

**10. 应保留的测试证据**
`perf.json`（时间戳/SRC 原始数据）、`test-results.json`、`environment.json`（音频设备段）。

**11. 状态**：未开始

## M2-T3 · Track A 音频桥接与第三方应用读取验证（含 NFR-02）

**1. Task ID 与目标**
经用户主动安装的、许可明确的合法虚拟音频路由工具（或既有测试端点）建立桥接：Runtime 输出 PCM → 桥接端点 → 第三方录音应用可枚举、选中、读取；完成 NFR-02（无 AI、48kHz 单声道 10ms 块，连续 30 分钟无持续断流，underrun 事件完整统计）。**本任务的产出不得表述为自研驱动**。

**2. 对应需求 FR / 架构 ADR**
- FR-002（受控环境验证）、FR-003、FR-006；ADR-004；基线 §2.2 Track A、§5.2、§9 M2-3、§7 NFR-02、§8（第三方组件许可与分发条件）。

**3. 前置依赖**
M2-T2。

**4. 允许修改的模块与文件范围**
- 修改：`platforms/windows/audio-bridge/`（桥接配置与适配文档；**不含第三方软件本体**）
- 修改：`runtime/device-bridge/`（音频 PCM 输出适配）
- 新建：`docs/licensing.md`（桥接工具许可审查记录）、`tests/performance/`（NFR-02 采样脚本）

**5. 实施步骤**
1. 候选桥接工具选型（用户确认安装）：许可证、分发条件、来源记录进 SBOM；**不默认随产品捆绑**（§2.2）。
2. 安装并配置虚拟端点；Runtime PCM 写入端点（经环回或直写，按工具机制实测确定并记录）。
3. 第三方录音应用（Audacity/录音机/浏览器 getUserMedia 音频，记录版本）枚举、选中、录制验证。
4. 录制内容一致性检查：固定测试音（正弦扫频/脉冲）录制回放比对（频谱/波形脚本比对）。
5. NFR-02 正式测量：30 分钟连续运行，underrun/断流事件统计与缓冲事件落盘（测量条件全记录）。
6. 桥接工具故障演练：关闭桥接工具 → Runtime 行为（降级静音/错误上报）记录。

**6. 自动化测试要求**
- 录制比对脚本（固定测试音的频谱断言）；30 分钟采样脚本输出 perf.json（断流次数、underrun 计数、水位）。

**7. 真实环境验收要求**
- 第三方应用真实读到音频（录制文件留证 + 比对结果）；**仅 Loopback 进程内验证不构成验收**。

**8. 完成标准（DoD）**
- 端到端音频链路可用且有 30min 证据；许可审查完成；文档明确标注「经合法第三方桥接，非自研驱动」。

**9. 风险及失败处理**
- 桥接工具不稳定/许可不兼容商用 → 更换候选或该 Track 降级为「实验性」；结论如实写进 G2 汇报（R-01 相关）。
- underrun 持续超标 → 音频写入节奏按 §5.3（音频设备节奏优先），排查后再测；禁止用加大缓冲掩盖问题而不记录。

**10. 应保留的测试证据**
`perf.json`（NFR-02 全量采样）、`test-results.json`（录制比对）、`screenshots/`（第三方应用识别端点）、`licensing-sbom.json`、`device-enumeration.txt`（音频端点枚举）。

**11. 状态**：未开始

## M2-T4 · 音视频同一 Session 联合运行与同步测量（NFR-04/05）

**1. Task ID 与目标**
同一 Session 内同时运行视频 Track（M1 链路）与音频 Track（M2-T2/T3 链路）：统一时钟域、可独立启停；完成 NFR-05（无 AI，A/V 相对时间偏差 ≤80ms 目标）与 NFR-04 的初步测量（麦克风输出新增时延 p95 ≤100ms 目标，注明测量路径）。

**2. 对应需求 FR / 架构 ADR**
- FR-003（两设备从统一 Runtime 读输出、独立启停）、FR-006；ADR-005；基线 §4.4（时间模型）、§9 M2-4、§7 NFR-04/NFR-05。

**3. 前置依赖**

**4. 允许修改的模块与文件范围**
- 修改：`runtime/media-core/`（Session 联合编排、时钟映射）、`runtime/gst-adapter/`（Pipeline Latency 配置）
- 新建：`tests/performance/`（同步测量）

**5. 实施步骤**
1. 单 Session 双 Track 编排：视频测试卡 + 音频脉冲同源启停；验证两 Track 独立 MUTED/PAUSED 不影响对方（§4.3）。

5. 独立启停矩阵：视频停/音频行、音频停/视频行、双双启停 × 状态机断言。

**6. 自动化测试要求**

**7. 真实环境验收要求**

**10. 应保留的测试证据**

## M2-T5 · 鲁棒性验证：启停、SRC、热插拔、休眠唤醒、权限撤销（NFR-08 初版）

**1. Task ID 与目标**
系统级鲁棒性清单：单独启停、采样率变化、USB 设备热插拔、系统休眠/唤醒、**麦克风权限撤销**（撤销后立即阻止新音频进入处理支路，缓冲按策略清空——§4.3）；采集权限相关 NFR-08 初版证据。

**2. 对应需求 FR / 架构 ADR**
- FR-006、FR-008、FR-009；ADR-010；基线 §9 M2-4、§4.3（关闭录音权限语义）、§7 NFR-08、§11-4（失败收敛：不得绕开授权自动回到真实麦克风）。

**3. 前置依赖**
M2-T4。

**4. 允许修改的模块与文件范围**
- 修改：`runtime/media-core/`（权限/恢复逻辑）、`runtime/gst-adapter/`、`tests/fault-injection/`

**5. 实施步骤**
1. 启停矩阵：设备级/Track 级/Session 级启停 × 顺序组合，状态机断言。
2. 采样率变化：切换系统默认格式/不同麦克风 → SRC 链路自动适配验证。
3. 热插拔：拔插 USB 麦克风/摄像头 → 设备消失/出现事件、Session 降级与恢复记录。

**6. 自动化测试要求**

**7. 真实环境验收要求**
- 全部场景在真实 Windows 上执行；权限撤销必须通过 OS 真实设置面板操作（截图），不得用进程内开关替代 OS 权限语义。

**8. 完成标准（DoD）**
- 全部场景行为符合预期或失败项有根因记录；无孤儿状态；NFR-08 初版证据入库。

- 权限撤销后残留数据 → **按 §11-5 处理：未授权保留的媒体按策略清空**；此为安全要求，不得妥协。

**10. 应保留的测试证据**
`test-results.json`（场景矩阵）、恢复时序日志、`screenshots/`（OS 权限面板）、`security-checklist.md`（撤销语义检查项）。
