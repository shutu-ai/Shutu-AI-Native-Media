## M5-T1 · Shutu Media Control GUI

**1. Task ID 与目标**
用户控制面：设备状态（摄像头/麦克风/采集/处理/发送状态显式展示，§11-2）、权限开关（采集、AI 参与、远程处理分离）、AI 开关与模型（Provider）选择、诊断导出（自动打包九文件证据）；可视化预览控制台（`apps/media-lab`）并入或共存。**不绕过 OS 隐私对话框**（§3.4 边界）。

**2. 对应需求 FR / 架构 ADR**
- FR-009（可见、批准、撤销）；ADR-005（Control & Trust Plane 的 UI 落地）；基线 §9 M5-1、§3.3、§11-1/2、§13（apps/、shutu-control）。

**3. 前置依赖**
G4 = GO。

**4. 允许修改的模块与文件范围**
- 新建：`apps/media-lab/`（或 `shutu-control`；技术栈按许可与维护性选择并记录）
- 修改：`runtime/media-core/`（控制面 API 暴露，仅控制通道、不碰热路径）

**5. 实施步骤**
1. 控制面 API 清单固化（走 M1-T4 控制通道；鉴权：仅本用户会话）。
2. 状态页：设备枚举状态、当前 Track/Session、AI Provider 与健康、来源标识（衔接 M4-T3）。
3. 权限页：采集（摄像头/麦克风分列）、AI 处理（本地/远程分离，§11-1）、撤销即时生效复用 §6.4-5 语义。
4. 模型页：已装 Provider 列表、切换、版本与许可显示（SBOM 可视化最小集）。
5. 诊断导出：一键收集 artifacts 九文件（脱敏，§11-5 日志无媒体原则）。
6. GUI 无障碍与错误提示（用户友好错误信息，编码风格规范）。

**6. 自动化测试要求**
- 控制面 API 集成测试（权限开关 → 运行时行为联动断言）；GUI 冒烟（启动、页签、导出）。

**7. 真实环境验收要求**
- 真机上从 GUI 撤销权限 → OS 级行为变化（设备输出改变）截图留证；**纯 UI 单元测试不构成验收**。

**8. 完成标准（DoD）**
- 全部页面可用；权限操作与运行时联动有证据；诊断导出文件 schema 合法。

**9. 风险及失败处理**
- GUI 直接操作设备注册（越权）→ 架构禁止：GUI 只走控制通道（ADR-006）；代码审查项。
- 预览工具独占设备（R-12）→ 预览用共享读取或复用虚拟设备流，测试多消费者共存。

**10. 应保留的测试证据**
`test-results.json`、`screenshots/`（权限联动前后）、`build.log`、`licensing-sbom.json`（GUI 依赖）。

**11. 状态**：未开始

## M5-T2 · 安装、升级、卸载与回滚（NFR-09）

**1. Task ID 与目标**
产品级安装器：全新安装、覆盖升级、卸载、失败回滚；设备注册冲突检查（已有同名/冲突虚拟设备时的行为）；`tools/uninstall-verify` 自动化残留检查（注册表、文件、进程、驱动实体——音频驱动项按 Track B 状态标注适用性）。

**2. 对应需求 FR / 架构 ADR**
- FR-001、FR-002、FR-008；ADR-003、ADR-004、ADR-010；基线 §9 M5-2、§7 NFR-09、§10.1 安装测试、§13（installer、uninstall-verify 需实施）。

**3. 前置依赖**
M5-T1（安装包含控制面组件）。

**4. 允许修改的模块与文件范围**
- 新建：`platforms/windows/installer/`、`tools/uninstall-verify/`
- 修改：`platforms/windows/virtual-camera/`（安装钩子按需）

**5. 实施步骤**
1. 安装器选型（MSI/WiX 或等效；记录选型理由与许可）。
2. 安装内容清单：虚拟摄像头注册、Runtime 服务/进程、控制面、contracts 资源；每项可独立卸载。
3. 冲突检查：安装前扫描同类虚拟摄像头注册与占用；冲突时给出明确指引（不静默覆盖）。
4. 升级路径：旧版本 → 新版本（配置迁移、设备重注册）；失败 → 回滚到旧版可用状态。
5. 卸载：停止进程 → 注销设备 → 删除文件/注册表 → 校验；非零退出有日志。
6. `uninstall-verify`：对注册表键、文件路径、运行进程、设备枚举做白名单比对，输出差异报告。

**6. 自动化测试要求**
- 安装-升级-卸载-重装循环脚本化（≥3 轮）；uninstall-verify 差异为零断言；失败注入（中断安装）→ 回滚验证。

**7. 真实环境验收要求**
- 真机全流程执行（含重启节点）；卸载后真实枚举确认设备消失；**安装器单测通过 ≠ 验收**。

**8. 完成标准（DoD）**
- 四路径（装/升/卸/滚）可重复；uninstall-verify 报告干净；冲突指引文档化。

**9. 风险及失败处理**
- 残留导致重装失败 → 残留清单化并修复安装器；不发布带残留版本（FR-008 硬要求）。
- 音频驱动部分不适用（Track B 未 GO）→ 清单中显式标注「不适用 + 原因」，不隐藏。

**10. 应保留的测试证据**
`build.log`（安装器构建）、`test-results.json`（循环测试）、uninstall-verify 差异报告、`screenshots/`。

**11. 状态**：未开始

## M5-T3 · 版本固化、工件校验、SBOM 封版与签名计划（无需授权）

**1. Task ID 与目标**
Beta 发布工件管理：版本号固化策略、全部发布工件 SHA-256 清单与校验工具、SBOM 封版审查（自 M1-T1 起逐依赖持续记录，此处做完整性/许可冲突/安全更新通道终审）、**签名计划文档**（二进制签名策略、驱动签名的边界与触发条件）。**本任务只输出计划与审查结论，不执行任何签名操作——签名执行属 M5-T9（AUTH_REQUIRED，ADR-011 D3）。**

**2. 对应需求 FR / 架构 ADR**
- FR-008、FR-009；ADR-004、ADR-010；基线 §9 M5-3、§8 依赖规则、§11-9、§12 R-06、§15.2。

**3. 前置依赖**
M5-T2（工件 = 安装器 + 组件）。

**4. 允许修改的模块与文件范围**
- 新建：`tools/`（校验脚本）、`docs/licensing.md`（终审结论）
- 修改：`docs/licensing-sbom.json`（封版 tag）

**5. 实施步骤**
1. 版本策略：semver + 组件版本映射表；contracts 协议版本纳入。
2. SHA-256 清单：构建流水线自动生成 `SHA256SUMS` + 校验脚本；篡改样例测试。
3. SBOM 封版审查：逐条核对许可证/分发条款/链接方式/安全更新通道（§8 字段全集）；静态链接与专利项单独标注；不合规项决策（替换/移除/降级为实验版）。
4. 签名计划文档：代码签名证书路径（用户采购决策项）、驱动签名仅列 Track B 条件分支与触发条件（Beta-L2 / Track B=GO）；**本任务不签署任何工件，不做任何授权操作**。
5. 计划移交：签名计划评审通过后登记 M5-T9 触发条件；执行前的 AUTH 流程（出示计划与影响、取得显式授权）属 M5-T9。

**6. 自动化测试要求**
- SHA-256 校验脚本（正/负样例）；SBOM schema 完整性检查（每条依赖九字段齐全）。

**7. 真实环境验收要求**
- 校验在真实构建工件上执行；SBOM 与磁盘实际依赖一致性抽查（版本号比对）。

**8. 完成标准（DoD）**
- 工件 + 清单 + 校验工具可用；SBOM 封版 tag 存在；签名计划成文且授权状态明确。

**9. 风险及失败处理**
- 许可冲突发现（R-06）→ 立即隔离该依赖出发布范围；降级为实验版标注（§15.2 兜底条款）。
- 签名成本不可接受 → 记录并触发 M5-T6 决策分支。

**10. 应保留的测试证据**
`SHA256SUMS`、校验测试输出、`licensing-sbom.json`（封版）、`decision.md`（签名计划文档 + M5-T9 触发条件登记）。

**11. 状态**：未开始

## M5-T4 · 应用兼容性矩阵

**1. Task ID 与目标**
系统化兼容性验证并形成矩阵：Windows Camera、Chromium `getUserMedia`、OBS 或同类采集工具、录音/波形工具、浏览器音频采集页；主流会议软件**按实际测试逐个添加，不得事先承诺全部可用**（§10.2 明文）；每项记录应用版本 + 结果 + 失败现象。

**2. 对应需求 FR / 架构 ADR**
- FR-001、FR-002、FR-003；ADR-009；基线 §10.2 最低组合、§9 M5-4、§15.2（支持应用清单清晰）。

**3. 前置依赖**
M5-T2（用安装器部署的正式形态测试）。

**4. 允许修改的模块与文件范围**
- 新建：`docs/compatibility-matrix.md`、`tests/integration/`（矩阵脚本）
- 允许修复：`runtime/`、`platforms/windows/virtual-camera/`（兼容性缺陷）

**5. 实施步骤**
1. 矩阵维度：应用 × 设备（Camera/Mic）× 场景（枚举/打开/长会话/切换/关闭）× 结果。
2. 逐格执行并记录（版本、时间、Build、现象、截图）。
3. 失败项分级：可修复缺陷 → 修复后复测；应用侧限制 → 记录为已知限制（不粉饰）。
4. 会议软件：选取 1~2 款实际安装测试；未测软件在文档中列「未验证」清单。
5. 矩阵随发布工件一起版本化（支持应用清单进入 G5 证据）。

**6. 自动化测试要求**
- 枚举/打开/关闭可脚本化的部分自动化；录制比对复用 M2-T3 脚本。

**7. 真实环境验收要求**
- 全部结论来自真实应用真实操作（截图/录制证据）；**任何「应当兼容」的推断不得写入矩阵**。

**8. 完成标准（DoD）**
- 最低组合全覆盖；矩阵文档完成并版本化；已知限制清单诚实完整。

**9. 风险及失败处理**
- 会议软件失败且不可修复 → 记录根因（如私有设备用法）；支持清单中移除并标注；不影响其余 Beta 交付（§10.2 边界）。

**10. 应保留的测试证据**
`compatibility-matrix.md`、`test-results.json`、`screenshots/`、`device-enumeration.txt`、`environment.json`。

**11. 状态**：未开始

**9. 风险及失败处理**
- 长稳测试失败 → 缺陷分级：P0 阻断 G5；P1 可带 KNOWN_ISSUES 进入 Beta 并公示。

**10. 应保留的测试证据**
`artifacts/G5/<run-id>/perf.json`、`test-results.json`、崩溃/恢复时序日志、清洁镜像验证报告、`screenshots/`。

## M5-T6 · 音频交付形态决策

**1. Task ID 与目标**
基于 Track B 终态与签名计划（M5-T3）、兼容性矩阵（M5-T4）做出交付决策：**双设备完整 Beta** 或 **摄像头正式 Beta + 音频独立实验版**（§9 M5-6 两分支原文）；输出对用户的透明说明文本（产品页/文档措辞），确保不虚假宣传（§5.2 Track A 成功不可描述为自研驱动）。

**2. 对应需求 FR / 架构 ADR**
- FR-002（生产级另设门禁）；ADR-004、ADR-010；基线 §5.2、§9 M5-6、§12 R-01、§15.2（未达标禁止声称完整交付）。

**3. 前置依赖**
M5-T3（签名计划明确）；M5-T9 到达任意终态（已完成 / NOT_RUN——未触发或未授权时按 ADR-011 D3 记录，决策按 L1 分支评估）。

**4. 允许修改的模块与文件范围**
- 新建：`docs/`（交付形态说明）
- 修改：`artifacts/G5/`（decision.md）

**5. 实施步骤**
1. 输入复核：Track B GO/HOLD/STOP/NOT_RUN + 签名计划（M5-T3）+ 签名执行状态（M5-T9：已完成或 NOT_RUN）+ 兼容矩阵音频列结果。
2. 分支判定表：双设备完整 Beta 的全部前置条件逐条核对（签名链达标、清洁安装、兼容性达标）。
3. 任一条件不满足 → 选「摄像头 Beta + 音频实验版」，音频部分标注实验性与桥接依赖（如 Track A）。
4. 撰写透明说明：交付范围、已验证应用清单、已知限制、签名状态。
5. 用户确认决策（此为产品口径决策，必须用户批准）。

**6. 自动化测试要求**
