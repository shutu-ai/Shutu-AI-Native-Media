## M4-T2 · 稀疏视频采样、语义事件与提示注入防护

**1. Task ID 与目标**
异步视频稀疏采样机制（Frame Sampler）：按配置采样率抽帧 → 视觉理解 Provider → SemanticEvent；**不可默认逐帧上传**（§9 M4-2 明文）；隐私授权独立于实时处理授权；同时把 ASR/视觉识别的文本按**不可信输入**处理：注入测试证明其不能触发系统命令、打开文件、泄露会话或更改设备策略（§11-6）。

**2. 对应需求 FR / 架构 ADR**
- FR-004（实时画面理解形态）、FR-009；ADR-005、ADR-007；基线 §4.6 场景 2（隐私授权、采样率、延迟容忍）、§9 M4-2、§11-6。

**3. 前置依赖**
M4-T1。

**4. 允许修改的模块与文件范围**
- 新建：`runtime/media-core/`（Frame Sampler）、`providers/native/`（视觉理解 mock/真实轻量模型）
- 修改：`contracts/media/`（语义事件 v0.2 字段）、`tests/security/`（注入测试集）

**5. 实施步骤**
1. Sampler 实现：可配置采样率（如 1fps/0.2fps）、按帧时间戳稀疏抽取、与实时管线异步解耦（有界队列）。
2. 视觉理解 Provider（mock 起步，可选轻量真实模型）：输入采样帧 → 输出 SemanticEvent（带媒体时间区间与关联 ID）。
3. 授权模型：视觉理解授权独立开关；撤销 → 采样停止 + 队列清空（§6.4-5 复用）。
4. 防注入：识别文本进入任何下游（日志、控制面、未来 Agent API）前经过转义/白名单处理；定义「文本不可触发动作」边界。
5. 注入测试集：构造含指令样文本的音视频输入（字幕注入、画面文字注入样例），断言：无命令执行、无策略变更、无会话信息泄露。

**6. 自动化测试要求**
- Sampler 采样率与队列有界测试；授权撤销断言；注入测试集全绿（§10.1 安全测试证据形态）。

**7. 真实环境验收要求**
- 稀疏采样在真实视频流上运行并记录实际采样率与事件；注入测试至少含一个真实 ASR 输出驱动的端到端样例。

**8. 完成标准（DoD）**
- 采样机制可用且默认稀疏；防注入边界实现并有测试证据；授权独立可撤销。

**9. 风险及失败处理**
- 逐帧上传倾向（隐私/性能风险）→ 默认采样率写入策略上限，超限需显式授权（§9 M4-2 明文）。
- 注入面遗漏（下游新增消费者未过闸）→ 防注入处理放 centrale 管道（事件出口统一转义），并写入 threat-model（M1-T1 建立的文档）。

**10. 应保留的测试证据**
`test-results.json`（注入集 + sampler 测试）、`perf.json`（采样率/时延）、`security-checklist.md`、`docs/threat-model.md` 更新记录。

**11. 状态**：未开始

## M4-T3 · Generated Video Track 测试提供者与 AI 来源透明性

**1. Task ID 与目标**
Generated Video Track 机制与测试提供者（预录视频/合成帧模拟生成式输出，不依赖商业模型）：生成 Track 与真实/滤镜 Track 并存、输出端可选；生成内容携带**明确的 AI 来源元数据**（§11-7 生成媒体透明性；经 Control API 可查，普通虚拟设备通道不保证第三方应用显示标识——如实记录该边界）。

**2. 对应需求 FR / 架构 ADR**
- FR-004（生成式视频形态）、FR-009（生成内容可识别）；ADR-005、ADR-007；基线 §4.6 场景 4（生成超时、帧率波动、备用画面）、§9 M4-3、§11-7。

**3. 前置依赖**
M4-T1。

**4. 允许修改的模块与文件范围**
- 新建：`providers/mocks/`（生成视频 Provider）、`runtime/media-core/`（Generated Track 类型与来源元数据）
- 修改：`contracts/media/`（来源元数据字段）、`apps/`（Control API 来源查询，最小）

**5. 实施步骤**
1. Generated Track 类型：origin=GeneratedAI 的 Track 生命周期（§4.3 复用）。
2. Mock 生成 Provider：预录片段/程序合成帧按时间轴输出，帧率可配置波动（模拟真实生成的不稳定）。
3. 来源元数据：每帧/每 Track 附 origin、provider_id、generation_time；Control API 查询接口最小实现。
4. 备用画面：生成超时 → 占位帧/用户已选静态画面（§6.4-2）；**不得泄露最后一次未经授权保留的历史视频帧**。
5. 帧率波动演练：输出帧率骤降 → 按质量策略丢帧/保持占位，下游应用表现记录。

**6. 自动化测试要求**
- 生成超时→备用画面断言；元数据完整性断言；帧率波动场景脚本化。

**7. 真实环境验收要求**
- 真机输出端观察到 Generated Track（截图留证，含 Control API 元数据查询记录）；第三方应用**不显示** AI 标识的边界如实记录在文档。

**8. 完成标准（DoD）**
- Generated Track 可用；来源元数据可查；超时降级有证据；透明性边界声明成文。

**9. 风险及失败处理**
- 生成内容回放旧帧泄露 → 备用画面策略测试钉死（§6.4-2 硬要求）。
- 提前接真生成模型 → 禁止（§9 M4-3 明文用预录/合成帧模拟）。

**10. 应保留的测试证据**
`test-results.json`、`screenshots/`、`security-checklist.md`（来源透明与帧泄露项）、Control API 查询日志。

**11. 状态**：未开始

## M4-T4 · A+V 关联输出、统一时间轴与过期生成帧丢弃

**1. Task ID 与目标**
Audio+Video 关联输出（如语音驱动内容的音画对齐基础）：联合 Track 的时间轴绑定、关联事件时间戳可追踪（G4 验收句）；音视频联合模型落后时的**过期生成帧丢弃**策略（严禁无限堆积，§6.4-4）与画面异常降级。

**2. 对应需求 FR / 架构 ADR**
- FR-004（语音驱动虚拟人物/联合形态的表达与运行）、FR-006；ADR-005；基线 §4.4（推理结果延迟到达）、§4.6 场景 3、§9 M4-4。

**3. 前置依赖**
M4-T2、M4-T3。

**4. 允许修改的模块与文件范围**
- 修改：`runtime/media-core/`（关联时间轴、丢弃策略）、`runtime/gst-adapter/`、`contracts/media/`（关联 ID 语义）
- 新建：`tests/integration/`（联合输出场景）

**5. 实施步骤**
1. 关联模型：A/V Track 关联 ID + 同步锚点（口型/事件级对齐的机制预留，§4.6 场景 3「共同时钟」约束）。
2. Mock 联合 Provider：音频段 + 对应生成帧成对输出（时间可故意偏斜）。
3. 偏斜检测与修复：时间戳偏斜 → 重采样/丢弃估算（§4.4：Provider 声明时间精度，由同步节点处理）。
4. 过期丢弃：生成帧错过呈现窗口 → 丢弃或按策略更新下一帧；队列上限断言（严禁堆积）。
5. 画面异常降级：联合输出异常 → 降级到 Generated Track 静态/占位（衔接 M4-T3）。

**6. 自动化测试要求**
- 偏斜注入矩阵（±各种偏移）→ 关联正确性断言；过期帧丢弃计数与队列水位断言。

**7. 真实环境验收要求**
- 真机输出端观察联合输出（音画同步性人工记录 + PTS 数据）；Mock Provider 允许，但输出路径必须真实。

**8. 完成标准（DoD）**
- 关联时间轴可追踪（事件 → 音视频区间双向可查）；丢弃策略有界并有证据。

**9. 风险及失败处理**
- 口型对齐精度达不到产品级 → 本任务交付机制与时延数据，产品级对齐明确标注为后续工作（§4.6 场景 3 属能力线，不阻塞主线）。

**10. 应保留的测试证据**
`perf.json`（偏斜/丢弃数据）、`test-results.json`、时间轴追踪示例（trace 记录）。

**11. 状态**：未开始

## M4-T5 · 「单模型替代多节点」mock 集成测试

**1. Task ID 与目标**
编写集成测试：同一用户目标可由「多节点组合路径」与「单个端到端模型路径」分别满足，且切换时**虚拟设备接口与既有应用零改动**（G4 验收句）；两个路径均用 mock Provider（不依赖商业模型，§9 M4-5 明文）。

**2. 对应需求 FR / 架构 ADR**
- FR-004；ADR-005、ADR-007（不固定 ASR→LLM→TTS 唯一模式的证明）；基线 §4.5（编排规则）、§9 M4-5。

**3. 前置依赖**
M4-T4。

**4. 允许修改的模块与文件范围**
- 新建：`tests/integration/`（单模型 vs 组合对比场景）、`providers/mocks/`（端到端 mock）
- **禁止**：修改 `platforms/windows/`（零改动是被测断言，不是实现目标）

**5. 实施步骤**
1. 选定对照场景：如「字幕 + 降噪」（多节点：M3-T2+T4）vs「端到端语音理解 mock」（单模型）。
2. 端到端 mock Provider：一次调用产出组合路径的等价输出（事件 + 效果标记）。
3. 编排切换测试：运行中组合→单模型→组合，设备枚举/帧流/应用侧无感知断言。
4. 输出等价性检查：事件序列与效果在容差内等价（比较器脚本）。
5. 接口稳定性取证：切换前后 `contracts/` 公共 API diff 为空 + 真机应用行为记录。

**6. 自动化测试要求**
- 切换序列自动化；等价性比较器；零改动断言（对 `platforms/` 与公共契约做 diff 检查）。

**7. 真实环境验收要求**
- 切换演练在真机链路执行；应用侧（Windows Camera/录音端点）无重启、无重枚举故障的记录留证。

**8. 完成标准（DoD）**
- 两路径可互换证据完整；零改动断言通过；mock Provider 复用入库。

**9. 风险及失败处理**
- 切换暴露隐式设备耦合 → 回修 `runtime/` 隔离边界（允许），重新断言；若需改 OS 侧则 G4 记 HOLD 并走 ADR。

**10. 应保留的测试证据**
`test-results.json`、零改动 diff 证据、`screenshots/`（切换期间应用行为）、`perf.json`。

**11. 状态**：未开始
