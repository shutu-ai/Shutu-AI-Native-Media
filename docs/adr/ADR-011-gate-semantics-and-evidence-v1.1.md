# ADR-011 · Gate 语义修订、交付分级与证据归档规范（任务体系 v1.1）

> **状态**：已接受（规划层修订，经用户验收指令 2026-11-11）
> **影响范围**：`docs/tasks/` 全族 + `AGENTS.md`；**架构基线 v1.0 零改动**
> **修订性质**：基线 §14.2 / §15 已含的语义（HOLD/STOP 为 Gate 合法产出、§15.1/§15.2 两级发布标准）在任务体系层的显式化与可判读化。本 ADR 不降低任何安全门槛。

## 1. 背景（验收发现的问题）

规划阶段验收发现 6 项问题：

| # | 问题 | 级别 |
|---|---|---|
| P1-1 | M2-T6（SysVAD Track B，AUTH·PENDING）被列为 M2-T7（G2 汇总）的硬依赖 ⇒ 授权未取得时 G2 永久不可达，可选 PoC 阻塞主线门禁 | P0 |
| P1-2 | Gate 汇总任务硬依赖上游「完成」⇒ 上游失败/阻塞时无法产出 §14.2 报告，而 HOLD/STOP 恰是 Gate 任务的合法产出 | P0 |
| P1-3 | M5-T3 将无需授权的封版/SBOM/签名计划与需授权的签名执行混装 ⇒ AUTH·PENDING 阻塞 SBOM 封版（R-06 终审） | P0 |
| P1-4 | G5 判定未区分交付等级 ⇒ Camera-only Beta 与完整双设备 Beta 验收条件冲突 | P0 |
| P1-5 | 缺少可持久化、可审计、保护敏感信息的证据索引与归档规范 | P1 |
| P1-6 | 虚拟设备注册、工具安装、系统服务重启等系统状态变更缺少统一确认机制 | P1 |

## 2. 决策

### D1 · NOT_RUN 合法终态（修 P1-1）

- 状态机新增终态 **`NOT_RUN`**：适用于**可选任务**因授权未取得、资源未到位等原因未执行的情形。`NOT_RUN ≠ 完成`、`NOT_RUN ≠ 失败`；必须在对应 run 的 `decision.md` 记录原因与复评触发条件。
- M2-T6 为**可选 PoC**：未获授权/无隔离测试机时记 `NOT_RUN`，**不阻塞 G2**。
- **安全门槛不变**：G2 = GO 的强制条件（同 Session 音视频运作、桥接标识非自研驱动、同步/恢复指标证据）原样保留；Track B 的产品化由 M5-T6 交付决策与 M5-T9 签名执行独立门禁把守，G2 = GO **不断言** Track B 可生产化。基线 §9「SysVAD PoC 给出 GO/HOLD/STOP」解读为「给出显式结论，结论可以是 NOT_RUN（未授权而未执行，同样显式记录）」。

### D2 · Gate 汇总任务 = AGGREGATE 语义（修 P1-2）

- 全部 6 个 Gate 汇总任务（M0-T7 / M1-T8 / M2-T7 / M3-T9 / M4-T6 / M5-T8）依赖类型改为 **`AGG`**：上游任务到达**任意终态**（已完成 / HOLD / STOP / BLOCKED / NOT_RUN）即可启动汇总。
- Gate 任务**必须产出** §14.2 十字段报告（报告必达）；`STATUS=GO ⇔ 全部强制条件通过`，否则 HOLD（可复评）或 STOP（需环境/方案级干预）。**报告可达性不因上游失败而丧失**。
- 里程碑内普通任务保持 `TASK_DEP` 硬依赖不变；跨里程碑仍由 `G(k) ≠ GO ⇒ M(k+1) BLOCKED` 把守。

### D3 · M5-T3 / M5-T9 拆分（修 P1-3）

- **M5-T3（无需授权）**：版本固化、SHA-256 工件校验、SBOM 封版审查、**签名计划文档**（只写计划，不执行任何签名）。
- **M5-T9（AUTH_REQUIRED · 条件触发）**：执行代码签名/驱动签名操作。触发条件：仅当交付等级为 Beta-L2 或 Track B = GO 时才有意义；未触发/未授权时记 `NOT_RUN` 并不阻塞 G5（见 D4）。
- 任务总数 50 → **51**（M5: 8 → 9）。M5-T8 仍为 G5 汇总任务；M5-T9 编号顺延属**文档化例外**，执行顺序位于 M5-T8 判定之前（若授权达成）。

### D4 · Beta-L1 / Beta-L2 双交付等级（修 P1-4）

- **Beta-L1（Camera-only / 受限交付）**：基线 §15.1 全部通过 + §15.2 中标注 `L1+L2` 的通用项全部通过 + 音频交付形态为 M5-T6 决策的 L1 分支（Track A 实验版或不交付）+ 签名状态如实标注。判定输出 `STATUS=GO(LEVEL=L1)`。
- **Beta-L2（完整双设备 Beta）**：§15.1 + §15.2 **全部**通过（含 §15.2-1 自研音频设备签名链达标或合法分发策略）。判定输出 `STATUS=GO(LEVEL=L2)`。
- G5 = GO **必须声明交付等级**；禁止将 L1 表述为完整双设备交付（基线 §15.2 兜底条款）。L2 的全部条件原样保留——**未降低任何安全门槛**。

### D5 · 证据索引与归档规范（修 P1-5）

- 新增 `docs/tasks/EVIDENCE_SPEC.md`：run-id 命名、run 级 `manifest.json` schema（文件清单 + SHA-256 + 脱敏标记 + 关联 commit）、提交入库的 `docs/evidence/EVIDENCE_INDEX.md` 索引（仅元数据）、归档（zip + SHA256SUMS）与保留期、脱敏规则（§11-5 延伸）。
- 审计链：任务 ID → run-id → manifest → git commit 四级可勾稽。

### D6 · SYS_CHANGE 系统状态变更确认机制（修 P1-6）

- 与 `AUTH_REQUIRED`（登记表级）并行的轻量机制 **`SYS_CHANGE`**：凡改变系统持久状态的操作——虚拟设备注册/注销、系统服务安装/重启、开发工具安装、环境变量/PATH 修改——执行前须：① 任务实施步骤显式标注 `[SYS_CHANGE]`；② 运行时向用户单次确认（操作内容、影响范围、回滚方法）；③ 写入该 run `decision.md` 的 `system_changes[]` 与 `environment.json` 增量。
- 驱动安装/测试签名/安全策略变化**仍走 AUTH_REQUIRED**，不降级为 SYS_CHANGE。

## 3. 后果

- 文档族升级 v1.1：MASTER_TASK_PLAN / TASK_DEPENDENCIES / ACCEPTANCE_MATRIX / AGENTS.md；各里程碑文件加修订注记。
- 任务总数 51；G5 判定语法升级为 `GO(LEVEL=L1|L2)`。
- 新增自动化一致性检查 `tools/check-task-consistency.py`（含失败/阻塞分支用例 S1–S3），纳入规划文档维护流程。
- 基线 v1.0 保持零改动；若未来基线本身修订（如 §14.2 语义变化），须另立 ADR 并升级基线版本号。
